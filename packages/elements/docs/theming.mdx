# Tokens & theming

Every visual value in Kimen resolves from a design token — zero hardcoded
values, enforced by lint. Tokens are layered:

1. **Primitive** — the raw foundation: color ramps, spacing and type scales
   (`--ki-space-md`, `--ki-font-size-heading-3`…). Never consumed by
   components directly.
2. **Theme** — each theme's selection from the primitives into the shared
   ramp names (`--ki-color-brand-500` is the onmars terracotta by default;
   loading the material3 stylesheet rebinds the same name to its baseline).
   This is what makes one-step re-theming possible.
3. **Semantic** — meaning, not appearance (`--ki-surface-s0…s5`,
   `--ki-text-high-em`, `--ki-outline-low-em`, `--ki-elevation-e1…e6`,
   `--ki-motion-duration-fast`). This is the layer a brand reassigns to
   re-theme everything.
4. **Component** — the public styling contract of each element
   (`--ki-button-primary-neutral-rest-bg`, `--ki-button-md-height`…).

Who reassigns which layer:

- **A theme** (a complete restyle, like material3 or a brand's own) may
  redefine the palette — the primitive and theme ramps, `--ki-color-*` —
  and the semantic tokens that do not fit it. Translucent variants
  (`--ki-color-brand-500-alpha-1`…) are mixes of their ramp step, so they
  follow a redefined step on their own.
- **An application** using a theme reassigns semantic tokens, and component
  tokens for one component, never palette steps: every semantic pair is
  contrast-checked against the theme's palette, and a step an application
  changes is checked by nobody.

## Themes

**Onmars** is the default theme (it is `tokens.css`, no attribute needed).
**Material 3** ships as the reference second theme and proves in CI, on
every commit, that reassigning the token layers alone restyles every
component:

```html
<link rel="stylesheet" href="@kimen/tokens/css" />
<!-- opt-in second theme -->
<link rel="stylesheet" href="@kimen/tokens/css/material3" />
<html data-ki-theme="material3">
```

A theme stylesheet carries only what it changes over the default theme, so
it is always loaded **alongside** `@kimen/tokens/css`, never instead of it.
An unknown `data-ki-theme` value — or a theme whose stylesheet was not loaded
— simply lands on the default theme. No runtime code involved anywhere.

## Color scheme

Both themes follow the OS by default and can be forced either way:

```html
<html data-ki-color-scheme="dark">   <!-- force dark -->
<html data-ki-color-scheme="light">  <!-- force light -->
<!-- no attribute: follows the system preference -->
```

The **Scheme** toolbar above drives exactly this attribute.

The scheme is one declaration, and the token stylesheet makes it: the root
gets `color-scheme: light dark` as a default, and `data-ki-color-scheme` pins
it to one side. Every scheme-dependent token is a single `light-dark()` value that
resolves from that declaration, so the tokens and the browser — page canvas,
scrollbars, native controls, autofill — always agree. A page that loads only
`@kimen/tokens/css` is coherent in both schemes.

Consequences worth knowing:

- Kimen follows the page's `color-scheme`, not `prefers-color-scheme`
  directly. The stylesheet's own declaration has zero specificity, so if
  your CSS declares the page's scheme (`html { color-scheme: light }`, before
  or after the token stylesheet) yours wins and the tokens stay light with
  it. A `<meta name="color-scheme">` alone does not: declare it in CSS.
- To reassign a scheme-dependent token, give both values:
  `--ki-surface-s0: light-dark(#fff, #111)`. A single value applies to both
  schemes.
- A scheme-dependent token only becomes a colour where it is used. Script
  that reads one with `getPropertyValue('--ki-surface-s0')` gets the
  `light-dark()` pair; read the computed `color` or `background-color` of an
  element that uses the token instead.

## Theming a subtree

Both attributes work on any element, not only on `<html>`. This is what an
island of generated UI embedded in someone else's page needs:

```html
<html>                                     <!-- onmars, follows the system -->
  <section data-ki-theme="material3">      <!-- material3 inside it -->
    <aside data-ki-color-scheme="dark">    <!-- material3, forced dark -->
      <div data-ki-theme="onmars">…</div>  <!-- back to the default theme -->
    </aside>
  </section>
</html>
```

- `data-ki-color-scheme` on an element forces the scheme for its subtree.
  It redeclares nothing: `light-dark()` resolves where a token is used.
- `data-ki-theme` on an element re-themes its subtree. `onmars` — or any
  name without a loaded stylesheet — returns the subtree to the default
  theme, which is how you opt a region out of the page's theme.
- The nearest declaration wins, independently for theme and for scheme.

A declaration restyles what **consumes** tokens; it does not paint the
element that carries it. Give a region its own surface the same way the page
contract gives the page one:

```css
.region {
  background-color: var(--ki-surface-s0);
  color: var(--ki-text-high-em);
}
```

### Reassigning tokens in a subtree

A custom property that aliases another one is resolved on the element that
**declares** it, and descendants inherit the result. The primary button fill
is `--ki-button-primary-neutral-rest-bg` → `--ki-surface-primary-med-em` →
`--ki-color-brand-500`: reassigning `--ki-color-brand-500` on a plain `<div>`
changes what reads that token directly and neither alias, so the button keeps
the page's colour. A themed subtree redeclares every token on its own root,
which recomputes every alias — name the subtree and reassign there:

```html
<section data-ki-theme="acme">…</section>
```

```css
[data-ki-theme='acme'] {
  --ki-color-gray-50: #e8f0f8;    /* s1 and everything built on it */
  --ki-color-brand-500: #0b57d0;  /* the accent and its translucent variants */
}
```

Every component in the section follows, hover washes and focus glows
included: the translucent variants are mixes of `--ki-color-brand-500`.

The same redeclaration means page-level reassignments made on `:root` do not
flow into a themed subtree: it starts from its theme's own values. Repeat
them for the subtree if you want both
(`:root, [data-ki-theme='acme'] { … }`). On a page with its own theme, a
subtree that adjusts a few tokens repeats that theme's name
(`<section data-ki-theme="acme" class="sheet">`, the `.sheet` rule after the
theme rule): another name starts it from the default theme and drops the
page theme. Your page's own aliases of Kimen tokens work the same way:
`--page-accent: var(--ki-surface-primary-low-em)` declared on `:root` alone
keeps the root's colour inside every region.

### Modes and your own theme

A preference mode (more contrast, reduced transparency) applies over any
theme on its own: under the mode, Kimen re-points each token it reassigns to
that token's mode token with `!important`, on the root and on theme roots.
A theme chooses its own mode values by setting the mode tokens,
`--ki-<mode>-<token>`, at normal priority. *Docs → Tokens reference →
Preference modes* lists every reassigned token and its mode token:

```css
[data-ki-theme='acme'] {
  --ki-outline-control: #8c857c;
  /* Only under more contrast */
  --ki-contrast-more-outline-control: light-dark(#4a4540, #c4bdb4);
}
```

Restating the token itself under the mode's media query no longer has any
effect: the mode wins. Move such values to the mode tokens.

### `color-scheme` in a theme

Leave it out: the token stylesheet declares `light dark` and
`data-ki-color-scheme` pins it with the specificity of one attribute. A
theme rule of that specificity or more (`[data-ki-theme='acme']`,
`:root[data-ki-theme='acme']`) overrides the attribute and breaks a
light/dark toggle. A theme that only works in one scheme declares that
default at zero specificity, loaded after the tokens:
`:where([data-ki-theme='acme']) { color-scheme: dark; }`.

## The page contract

Tokens are custom properties: loading them paints nothing. The page
contract, which pages load with them, paints the page from them — background
from `--ki-surface-base`, text from `--ki-text-high-em`, and the body
typeface:

```html
<link rel="stylesheet" href="@kimen/tokens/css" />
<link rel="stylesheet" href="@kimen/tokens/css/base" />
```

It publishes no tokens of its own — it only consumes them, so it never widens
the token surface — and it declares no colour scheme: the token stylesheet
owns that.

Until a tag registers, the page contract also lays out the items of Kimen
groups (segments, radios, checkboxes, options, menu, list, tab, tree, step,
timeline and navigation items) as blocks, so a late or failed component
script leaves a readable list instead of one run of text. The rule paints
nothing, has zero specificity and stops matching once the tag is defined.

Skipping it is supported in both schemes. Without it the page keeps the
browser's own canvas and text colour for the active scheme, and every
component stays legible on it. That is measured, not assumed:
`bare-page.browser.spec.ts` loads the token stylesheet alone, walks the flat
tree through shadow boundaries, composites the real backdrop behind every
rendered string — down to the browser canvas — and holds all 29 components to
4.5:1 under a dark system preference.

color from the live token):

  {['s0', 's1', 's2', 's3', 's4', 's5'].map((s) => (
    <div
      key={s}

        inlineSize: '5.5rem',
        blockSize: '3.5rem',

    >
      {`surface-${s}`}

  ))}
</div>

## The fidelity families

The MarsUI fidelity pass promoted four visual behaviors — motion, glass,
bevels and elevation — from per-component styling into token families, so
themes control all of them the same way they control color. The full token
tables live in *Docs → Tokens reference* (generated); this is the model.

### Motion

Three semantic scales: **durations** (`--ki-motion-duration-instant`,
`-fast`, `-short-1…4`, `-medium-1…4`, `-long-1…4`), **easings**
(`--ki-motion-easing-standard`, `-out`, `-emphasized`, `-emphasized-out`, plus
`-accelerate`/`-decelerate` variants) and **distances**
(`--ki-motion-distance-xs/sm/md`) for travel-based transitions. Components
consume them through their own motion tokens, for example:

```css
ki-dialog {
  --ki-dialog-motion-duration: var(--ki-motion-duration-fast);
  --ki-dialog-motion-easing: var(--ki-motion-easing-emphasized-out);
}
```

The `prefers-reduced-motion` contract is part of the family: components
declare their transitions only under
`@media (prefers-reduced-motion: no-preference)`, so a reduced-motion user
gets instant state changes — not shorter animation. Themes may retune
durations and easings, never bypass that gate.

### Glass

Calma uses solid dialog and tooltip fills and a single-color select listbox
tint. Each surface accepts an optional `-bg-image` token layered over its `-bg`
color, and reads its complete filter from a token such as
`--ki-dialog-backdrop-filter`. Material 3 uses solid fills. Set
`--ki-effect-component-backdrop-filter` to `none` at the theme root to turn
off the shared effect, including the select listbox. A component token can
still set its own complete filter value, such as `blur(12px)`.

To make a tooltip flat, set the fill, turn off the image and the filter, and
use the same color for the arrow edges:

```css
:root {
  --ki-effect-component-backdrop-filter: none;
  --ki-tooltip-bg: var(--ki-surface-s2);
  --ki-tooltip-bg-image: none;
  --ki-surface-image-tooltip-arrow-start: var(--ki-tooltip-bg);
  --ki-surface-image-tooltip-arrow-end: var(--ki-tooltip-bg);
}
```

Calma and reduced transparency use `none` for both shared filters. Use
`--ki-effect-component-listbox-backdrop-filter` to give a glass theme a separate
listbox filter. Material 3 keeps a zero-radius blur in its standard mode.

### Bevels

Raised controls carry a per-side edge: a hairline `border` for the top
light plus a distinct `border-bottom` for the seated edge, as token pairs —
`--ki-button-{primary|secondary|tertiary}-rest-border-bottom` (ki-icon-button
paints with the same tokens) alongside the per-state `-border` tokens.
Flat variants (`quaternary`, `ghost`) declare no bevel. Themes that want
flat buttons resolve the pair to the same color or to none.

### Elevation

One semantic ramp, `--ki-elevation-e1` through `--ki-elevation-e6`, is the
shadow vocabulary every component draws from, plus component effect shadows
(`--ki-effect-component-{primary|secondary}-{default|hover}-shadow`,
`--ki-effect-small-dark-shadow`) for the raised-control treatment. Restyle
elevation by reassigning the ramp — components never hardcode a shadow.

## Customization order

When you need to customize a component, reach for surfaces in this order —
if a consumer would ever need `!important`, that is an API bug to report:

1. **Tokens** — reassign at `:root` (theme-wide) or on a themed subtree
   (see *Theming a subtree*).
2. **`::part()`** — style exposed parts for one-off structural tweaks.
3. **Slots** — replace content entirely.
