# @kimen/catalog

> Kimen neutral catalog and guardrail boundary: schema-constrained specs rendered from a closed component catalog. The durable asset (constitution Art. VIII).

## When to use

Any boundary where agent-emitted JSON must become Kimen UI: validate specs standalone, render them with the guardrail enforced, stream them progressively, or keep a long-lived surface current with id-addressed batches. Both protocol adapters and any custom transport build on it.

## When not to use

Hand-authored pages that never render agent output — use @kimen/elements directly.

## Entry points

- `validateUiSpec(input, options?) => ValidationReport`: Accepts or rejects an agent-emitted UI spec against the catalog in use — the built-in generated catalog, or a registered one passed as options.catalog — before anything renders. The report lists every issue with a code (unknown-component, unknown-prop, invalid-prop-type, missing-required-prop, prop-out-of-range, unknown-slot, undeclared-action, undeclared-event, invalid-child, action-not-allowed, collect-without-action, collect-unknown-node, collect-no-value, collect-key-conflict, collect-budget, url-scheme, url-origin, invalid-id, duplicate-id, forbidden-key, size-budget, depth-budget, malformed-spec), a path into the spec document and the offending value.
- `renderUiSpec(input, options) => RenderResult`: Validates and renders a spec into options.surface through the guarded renderer: only components of the catalog in use render (options.catalog selects it; absent, the built-in catalog applies) plus the native primitives it carries, only actions declared in the spec dispatch, by name or one per declared event (delivered as data to options.onAction, with the live values of the fields a node collects once each of them is valid), unknown props are rejected and no code path executes from spec data. Failures come back as diagnostics naming rule, path and value; nothing attaches on failure.
- `preflightUiSpec(input, options?) => RenderResult`: The guarded renderer's verdict without a DOM: runs exactly the preparation renderUiSpec runs before its first attach (purity wall, version gate, payload budget, catalog validation, then the depth, node-count, tag, activation and prop-name guards) and renders nothing. Use it at a DOM-less boundary — an MCP server, a service that checks specs before forwarding them — so that "valid" means "the renderer will paint it"; validateUiSpec alone accepts specs the renderer's tighter budgets refuse.
- `createStreamingRenderer(options) => StreamingRenderer`: Progressive rendering over a streamed spec: each push(node) validates one top-level subtree and attaches it only when fully valid; an invalid node fails closed while previously attached content remains, and the render budgets bind the accumulated stream. The catalog in use is fixed at creation via options.catalog.
- `createLiveSurface(options) => LiveSurface`: A long-lived surface changed through atomic batches of insert, set, text, remove, replace and reset ops addressed by stable node ids: apply(batch) validates the whole batch and the state it would produce (purity wall, per-batch budgets, optional ifRevision, catalog, guards, state budgets) before any DOM write, rejects it whole with diagnostics while the surface stays live, and otherwise touches only the attributes, text and subtrees it names so focus, typed values and scroll survive. A rejection is the return value, never a throw, and leaves earlier batches applied: several batches are not one change. The five limits (64 ops and 65,536 bytes per batch; 512 nodes, 32 levels and 262,144 bytes of state) are host options at creation, lower or higher than the defaults. A batch may name a focus node: if the batch leaves keyboard focus nowhere, it goes there; focus that is somewhere never moves. No set, replace or remove overwrites or discards checked/open/selected/value the user changed unless forced and allowed by the host; a dialog the person closed is reopened with open: false, then open: true in a later batch. A reset op returns a control to its spec value, or empties it, without force or host permission, only once what it holds left in an action; input no action carried is kept and the batch is rejected as unsent-user-input. Action events carry id, current path, revision and live data; snapshot() returns deep-frozen plain data. The batch and op shapes are exported as the LiveBatch and LiveOp types.
- `createCatalog(definition, options?) => CatalogCreationResult`: Registers your own components behind a data-only JSON facade — the exact entry shape of the generated catalog (tag, usage guidance, typed prop constraints, slots, events) — and returns a deeply frozen catalog that validateUiSpec and both renderers accept via options.catalog. The definition is untrusted input: it crosses the same purity wall as UI specs, tags must be conservative custom-element names, collisions with the extended catalog fail closed, usage guidance is mandatory, and every rejection is a RegistrationIssue naming code, path and offender. Pass { extend: catalogData } to compose with the built-in components, or omit it for a standalone catalog.
- `DEFAULT_RENDER_BUDGETS`: The declared render budgets (maxDepth 32, maxNodes 512, maxBytes 262144). A spec exactly at a budget passes; one beyond it is rejected before any node attaches. Hosts may lower or raise them via options.budgets; the renderer never renders past the ones in force. Standalone validation has its own ceilings, VALIDATION_MAX_BYTES (262144 UTF-8 bytes, overridable per call with maxBytes) and VALIDATION_MAX_DEPTH (256).
- `catalogData`: The generated catalog document itself: one entry per opted-in ki-* element and per native primitive with typed props, events, slots and when-to-use guidance, plus the elements version it derives from. Its schema version is exported as CATALOG_SCHEMA_VERSION.
- `NATIVE_PRIMITIVE_TAGS`: The closed set of native HTML elements a spec may carry next to catalog components: h2, h3, h4, p, strong and em for text, img for images, div for layout, and table, caption, thead, tbody, tr, th and td for read-only tables. They take the host page's typography, carry only their declared attributes (img: src under the URL policy, alt that is a description or exactly empty for decoration, width, height; div: direction, gap on the --ki-space-* steps, align, justify, wrap; th: scope col or row), keep a content model (a table part sits only in its own parent), never bind an action, and lay out through the CSSOM so a CSP without unsafe-inline styles holds. They come with the built-in catalog and with catalogs that extend it; a consumer definition can never declare one.
