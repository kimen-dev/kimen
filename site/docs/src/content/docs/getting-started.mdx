Kimen ships two packages you install together: **`@kimen/elements`** (the
`ki-*` web components) and **`@kimen/tokens`** (the design-token stylesheets
that give them their appearance). Components resolve every visual value from
tokens, so loading a token stylesheet is not optional styling — it is the
styling.

:::note
Kimen is **pre-v1**. The packages build from the
[repository](https://github.com/kimen-dev/kimen) today and publish to npm
with trusted publishing and signed provenance at v1.0.0; the API documented
here is the release contract.
:::

## Install

```sh
npm install @kimen/elements @kimen/tokens
```

## Load a theme

One stylesheet is required: a theme (`css` is the default **onmars** theme).
Load the **page contract** (`css/base`) with it:

```ts
import '@kimen/tokens/css'; /* onmars theme + color-scheme, light + dark */
import '@kimen/tokens/css/base'; /* page contract: page background, text color, body font, layout before registration */
```

The theme stylesheet declares every `--ki-*` token and the `color-scheme`
they resolve from, so the browser paints its canvas, scrollbars and native
controls in the same scheme as the components: a page that loads nothing
else stays legible for a visitor who prefers dark — measured across the component suite. That declaration is a default with zero specificity, so a
`color-scheme` your own CSS sets on the page wins and the tokens follow it.

The page contract paints the page itself from the tokens — background from
`--ki-surface-base`, text from `--ki-text-high-em`, and the body font family.
It declares no color scheme. Until the elements register, it also lays out
the items of Kimen groups one per line — segments, radios, checkboxes,
options, and menu, list, tab, tree, step, timeline, sidebar and mobile-nav
items — so their labels do not run together while the registration code
loads; it stops applying to each tag once it is defined. See
[Themes &amp; color schemes](/docs/guides/theming/) for the full
contract.

## Register the elements

Register everything at once with the lazy loader (each component's code
loads on first use):

```ts
import { defineCustomElements } from '@kimen/elements/loader';

defineCustomElements();
```

Or register only what you use, tree-shakably, from each element's subpath:

```ts
import { defineCustomElement as defineKiButton } from '@kimen/elements/ki-button';

defineKiButton();
```

## Use a component

<Demo
  code={`<ki-button variant="primary" tone="success" size="md">
  Save changes
</ki-button>`}
/>

That is the whole model: HTML in, standard DOM events out. Form controls
participate in native `<form>` submission with no framework bindings — see
[Framework integration](/docs/guides/frameworks/).

## Color schemes

Both themes follow the operating system by default and can be forced either
way with one attribute — no runtime code involved:

```html
<html data-ki-color-scheme="dark">  <!-- force dark -->
<html data-ki-color-scheme="light"> <!-- force light -->
<!-- no attribute: follows prefers-color-scheme -->
```

## A second theme, one attribute

The **material3** reference theme proves the theming model: load its
stylesheet and set one attribute, and every component re-skins with zero
component changes.

```html
<link rel="stylesheet" href="@kimen/tokens/css" />
<link rel="stylesheet" href="@kimen/tokens/css/material3" />
<html data-ki-theme="material3">
```

An unknown `data-ki-theme` value matches no selector and the document simply
stays on the default theme.
