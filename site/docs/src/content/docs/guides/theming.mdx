Every visual value in Kimen resolves from a design token — zero hardcoded
values, enforced by lint. A theme is nothing but a set of token assignments,
so re-theming is a stylesheet plus one attribute, with no component changes
and no runtime code.

Tokens are layered (the [Design tokens guide](/docs/guides/tokens/)
covers each layer in depth):

1. **Palette** — the primitive and theme ramps (`--ki-color-brand-500`,
   `--ki-color-gray-100`, `--ki-space-md`). Components never read them
   directly; the semantic layer does.
2. **Semantic** — meaning, not appearance (`--ki-surface-s0…s5`,
   `--ki-text-high-em`, `--ki-outline-low-em`). This is the layer a brand
   reassigns to re-theme everything.
3. **Component** — the public styling contract of each element
   (`--ki-button-primary-neutral-rest-bg`, `--ki-button-md-height`). Each
   component page lists its own under *CSS custom properties*.

### Who reassigns what

- **A theme** is a complete restyle, like Material 3 or your brand's own. It
  may redefine the palette (`--ki-color-*` ramps) and the semantic tokens
  that do not fit it. Material 3 does both. A translucent variant such as
  `--ki-color-brand-500-alpha-1` is a mix of its ramp step, so a theme that
  redefines `--ki-color-brand-500` gets matching variants without restating
  them.
- **An application** that uses a theme reassigns semantic tokens, and
  component tokens for a single component. It leaves the palette alone:
  every semantic pair is contrast-checked against the theme's palette, and a
  palette step an application changes is checked by nobody.

## Themes

**Onmars** is the default theme — it is `tokens.css` itself, no attribute
needed. **Material 3** ships as the reference second theme and proves in CI,
on every commit, that reassigning the token layers alone restyles every
component:

```html
<link rel="stylesheet" href="@kimen/tokens/css" />
<!-- opt-in second theme -->
<link rel="stylesheet" href="@kimen/tokens/css/material3" />
<html data-ki-theme="material3">
```

An unknown `data-ki-theme` value simply matches no selector: the document
stays on the default theme.

## Theming a region

`data-ki-theme` works on any element, not only on `<html>`. An element that
carries it redeclares every token, which recomputes every alias from the
values on that element. That makes it the place to restyle a region, palette
included. Any name works; a name without a theme stylesheet starts from the
default theme:

```html
<section data-ki-theme="cyanotype">…</section>
```

```css
[data-ki-theme='cyanotype'] {
  --ki-color-gray-50: #e8f0f8;   /* the surfaces built on it follow */
  --ki-color-gray-100: #d9e6f2;
  --ki-color-brand-500: #0b57d0; /* and so do its translucent variants */
}
```

Inside the section every semantic surface, text, tint and hover wash
resolves from that palette.

Without the attribute, the same rule does much less. A custom property that
aliases another, such as `--ki-surface-s1: var(--ki-color-gray-50)`, is
resolved on the element that declares it, and Kimen declares its tokens on
the root and on theme roots. On a plain element the palette token changes
and nothing that aliases it does, so the region keeps the page's surfaces.
Your own aliases behave the same way: declare a page alias such as
`--page-accent: var(--ki-surface-primary-low-em)` on
`:root, [data-ki-theme]`, not on `:root` alone, so each themed region
recomputes it.

The attribute restyles what reads tokens. It paints nothing itself, so give
the region its surface:
`background-color: var(--ki-surface-s0); color: var(--ki-text-high-em)`.

## Color scheme

Both themes follow the OS by default and can be forced either way, on the
document root or on any element:

```html
<html data-ki-color-scheme="dark">   <!-- force dark -->
<html data-ki-color-scheme="light">  <!-- force light -->
<!-- no attribute: follows the system color scheme -->
```

This site's theme toggle drives exactly this attribute, so every live demo
on these pages follows it.

The scheme is one declaration, and the token stylesheet makes it: it sets
`color-scheme: light dark` on the root, and `data-ki-color-scheme` pins it
to one side. Every scheme-dependent token is a single `light-dark()` value
that resolves from that declaration, so the tokens and the browser — page
canvas, scrollbars, native controls, autofill — always agree. A page that
loads only `@kimen/tokens/css` is coherent in both schemes.

The root declaration is a default with zero specificity. If your page is
deliberately single-scheme and already says so in its own CSS
(`html { color-scheme: light }`, before or after the token stylesheet), your
declaration wins and the tokens follow it. It has to be CSS: a
`<meta name="color-scheme">` alone does not pin the page.

### `color-scheme` in a theme

`data-ki-color-scheme` is the scheme switch, and it works by specificity: its
rule, `[data-ki-color-scheme='dark'] { color-scheme: dark }`, has the
specificity of one attribute. A theme that declares `color-scheme` with that
specificity or more overrides it, and a light/dark toggle stops working:

```css
/* Breaks the toggle: (0,2,0) beats [data-ki-color-scheme] on the root */
:root[data-ki-theme='acme'] { color-scheme: light dark; }

/* Breaks it too when loaded after the tokens: (0,1,0) ties, and order wins */
[data-ki-theme='acme'] { color-scheme: dark; }
```

Leave `color-scheme` out of a theme: the token stylesheet already declares
`light dark` and the attribute pins it. A theme that only works in one
scheme declares that default at zero specificity, in the theme stylesheet
loaded after the tokens, so the attribute still wins:

```css
:where([data-ki-theme='acme']) { color-scheme: dark; }
```

### The page contract

Tokens are custom properties: loading them paints nothing. The opt-in page
contract paints the page from them — background from `--ki-surface-base`,
text from `--ki-text-high-em`, and the body family:

```html
<link rel="stylesheet" href="@kimen/tokens/css" />
<link rel="stylesheet" href="@kimen/tokens/css/base" />
```

It publishes no tokens of its own — it only consumes them, so it never
widens the token surface — and it declares no color scheme: the token
stylesheet owns that.

It also covers the moment before the component scripts run. An unregistered
custom element is an inline box, so the items of a group run together:
three `ki-segment` labels read as one word. Until each tag registers, the
page contract lays out segments, radios, checkboxes, options and the items
of menus, lists, tabs, trees, steppers, timelines and navigation as blocks,
one per line. The rule paints nothing, has zero specificity, and stops
matching the moment a tag registers.

Skipping it is supported in both schemes. Without it the page keeps the
browser's own canvas and text color for the active scheme, and every
component stays legible on it. That is measured rather than assumed: on a
page loading only the token stylesheet, with the visitor's OS set to dark,
all 29 components hold 4.5:1 for every rendered string.

## More contrast and less transparency

Both themes answer two accessibility preferences of the person, in both
schemes, through tokens alone:

- **More contrast** (`prefers-contrast: more`): neutral text — body,
  secondary, labels, helper and placeholders — measures 7:1 or more against
  the surface behind it, neutral control boundaries 4.5:1, separators and
  container edges 3:1, and the keyboard focus ring is 3px thick. Text on
  brand and tone fills keeps 4.5:1, and disabled controls keep their
  standard look, so they never read as operable.
- **Less transparency** (`prefers-reduced-transparency: reduce`): every
  surface that holds content — menus, tooltips, dialogs, glass buttons,
  badges, alerts — becomes the opaque surface it reads as over the page, and
  nothing blurs what is behind it. Hover and press washes and the modal
  backdrop keep their translucency. More contrast implies it: a contrast
  ratio over glass depends on what is behind the glass.

A page can switch either mode on without the system preference, for an
in-app accessibility setting or for browsers that do not report it (Safari
has no `prefers-reduced-transparency`):

```html
<html data-ki-contrast="more">
<html data-ki-transparency="reduce">
```

A declaration only ever adds: no value switches a mode off against the
person's preference. It takes effect on the document root and on a theme
root (an element with `data-ki-theme`), and a theme root nested inside one
that declares it follows it. A region that needs its own contrast declares
it next to its theme: `<section data-ki-theme="material3"
data-ki-contrast="more">`.

### Modes and your own theme

A mode applies over your theme without your theme doing anything. Each
token a mode reassigns, such as `--ki-outline-control` or
`--ki-text-supporting`, has a mode token that holds its value under the
mode: `--ki-contrast-more-outline-control`,
`--ki-reduced-transparency-surface-primary-tint`. Under the mode, Kimen
re-points the token to its mode token with `!important`, on the root and
on every theme root, so the mode wins whatever your theme sets.

To choose your own mode values, set the mode tokens in your theme, at normal
priority. The generated [token reference](/docs/tokens/reference/)
(*Preference modes*) lists every reassigned token, its mode token and
Kimen's value:

```css
/* Your theme, loaded after the token stylesheet */
[data-ki-theme='acme'] {
  --ki-outline-control: #8c857c;
  /* Used only under more contrast */
  --ki-contrast-more-outline-control: light-dark(#4a4540, #c4bdb4);
}
```

Your own value must meet the mode's floor: 4.5:1 for control boundaries and
7:1 for neutral text under more contrast; an opaque fill under reduced
transparency. A theme that restated the token itself under the mode's media
query, as earlier versions of this guide advised, now loses to the mode:
move those values to the mode tokens. A theme on `:root` sets them on
`:root`.

## Density

Any element can make its region compact — a data table, a toolbar, a dense
settings panel — with one attribute:

```html
<section data-ki-density="compact">…</section>
<div data-ki-density="default">…</div> <!-- back to the default inside it -->
<html data-ki-density="compact">        <!-- the whole page -->
```

Compact is Material's −2 step: controls and rows 8px shorter (40 → 32 in
onmars, 48 → 40 for material3 fields) and container padding and gaps ×0.75
(16 → 12). Text, icons, radius, borders, focus rings and content sizes
(avatar, badge, QR, progress, video) keep their size, and the `size` props
still pick a size within the density. The nearest declaration wins, theme
regions nested inside a compact region stay compact, and unknown values are
ignored.

No target ever drops under 24 × 24 CSS px (WCAG 2.5.8): every scaled
control floors its size at `--ki-density-target-min`, so in compact the
extra-small and small sizes can coincide at 24px. Two tokens carry the
step, and you can set your own: `--ki-density-control-offset` (added to block
sizes) and `--ki-density-space-scale` (multiplies padding and gaps).

```css
[data-ki-density='compact'] { --ki-density-control-offset: -4px; }
```

For touch-first surfaces — a kiosk, a mobile layout — declare `touch`
instead:

```html
<section data-ki-density="touch">…</section>
```

Touch is one +4px step (medium controls 40 → 44px, material3 fields
48 → 52px) with 44 × 44 CSS px pointer targets (WCAG 2.5.5, Apple's HIG).
Checkboxes, radios, switches, icon buttons and the alert's dismiss control
keep their painted size and their place: their target extends invisibly
around them instead. Text, icons and container spacing do not change. Touch
and compact nest in each other like any density, and `--ki-density-target-min`
sets the target (`48px` for Material's 48dp).

Kimen never switches to touch by itself. To follow the pointer, put the
touch values on the page root in your own stylesheet:

```css
@media (pointer: coarse) {
  :root {
    --ki-density-control-offset: var(--ki-space-xs);
    --ki-density-space-scale: var(--ki-scale-unit);
    --ki-density-target-min: var(--ki-size-target-touch);
  }
}
```

Leave room between small touch controls: an extended target reserves no
space, so two controls closer than 44px centre to centre share the overlap.
The target is centred on what the control paints, so it also reaches past
the control's leading edge (up to 13px for an 18px checkbox) and can lie over
content right before it; an ancestor that clips its overflow cuts it.

## Customization order

When you need to customize a component, reach for surfaces in this order —
if a consumer would ever need `!important`, that is an API bug to report:

1. **Tokens** — reassign at `:root` (theme-wide) or on a theme root
   (`[data-ki-theme]`) for a region; a component token can also go on one
   component.
2. **`::part()`** — style exposed parts for one-off structural tweaks.
3. **Slots** — replace content entirely.
