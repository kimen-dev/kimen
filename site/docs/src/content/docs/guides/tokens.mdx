title: Design tokens
description: The Kimen token model — layers, families, and how to customize components without forking them.
---

Kimen components carry **zero hardcoded visual values** — a lint gate fails
any color, size, radius, shadow or font that does not resolve from a
`--ki-*` custom property. That single rule is what makes theming one
attribute, keeps customization from becoming forking, and lets a contrast
gate hold every token pair to WCAG numbers in CI.

## The layers

1. **Palette** — the primitive and theme ramps, with no opinion about use:
   `--ki-color-brand-500`, `--ki-color-gray-900`, `--ki-space-md`,
   `--ki-font-size-heading-3`. Components never consume these directly.
   A theme may redefine them; translucent variants such as
   `--ki-color-brand-500-alpha-2` are mixes of their ramp step and follow it.
2. **Semantic** — meaning, not appearance: `--ki-surface-s0…s5` (the surface
   elevation scale), `--ki-text-high-em` / `--ki-text-med-em` (text
   emphasis), `--ki-outline-low-em`. Reassign this layer and an entire
   product restyles. The material3 reference theme redefines both this layer
   and the palette.
3. **Component** — the public styling contract of each element:
   `--ki-button-primary-neutral-rest-bg`, `--ki-dialog-backdrop-filter`,
   `--ki-alert-*`. Every component page lists its own tokens in its
   generated *CSS custom properties* table.

## Loading them

A page loads the token **core** once, `@kimen/tokens/css/core`, and one sheet
for every `ki-*` tag it uses, named like the element import:
`@kimen/tokens/css/ki-button` beside `@kimen/elements/ki-button`. The core
holds the palette and semantic layers; each tag's sheet holds the component
tokens that tag needs, including those of the components it renders. The
simple alternative is the full sheet, `@kimen/tokens/css`, with every token
in one stylesheet: better for a page that uses most of the catalog or cannot
list its tags in advance. See
[Getting started](/docs/getting-started/#load-a-theme).

## The families

Beyond color, the token surface covers everything a theme wants to control:

- **Typography** — families (`--ki-typography-family-body`, `-display`,
  `-mono`, `-serif`), sizes and weights.
- **Elevation** — a six-step scale, `--ki-elevation-e1` through
  `--ki-elevation-e6`.
- **Motion** — durations (`--ki-motion-duration-instant`, `-fast`),
  easings (`--ki-motion-easing-emphasized`, `-spring`) and distances
  (`--ki-motion-distance-xs/sm/md`). Components gate animation behind
  `prefers-reduced-motion`.
- **Effects** — shadows and glass surfaces
  (`--ki-effect-component-primary-default-shadow`,
  backdrop blur and gradient pairs consumed by dialog and tooltip).

The authoritative list is always the generated reference, never prose —
see [the token reference](/docs/tokens/reference/).

## Optional theme fonts

The typography tokens never fetch fonts. If you self-host your fonts, use
the family tokens with your own `@font-face` rules.

- **onmars v2** uses Instrument Sans for body text and Newsreader for display
  text. Import `@kimen/tokens/css/onmars-fonts.css` alongside the tokens for
  the upright Latin variable faces. Earlier onmars tokens use Inter.
- **Material 3** uses Roboto for body and display text. Self-host it
  alongside `@kimen/tokens/css/material3`. The optional
  `@kimen/tokens/css/material3-fonts.css` provides a local
  `'Roboto Fallback'` alias you can place between Roboto and `system-ui`.

To preload a font used in the initial viewport, use the URL that your build
emits in the stylesheet's `url()`, with `as="font"`, `type="font/woff2"`
and `crossorigin` on the preload link. Find example stacks and a preload
snippet in the [tokens package README](https://github.com/kimen-dev/kimen/blob/main/packages/tokens/README.md#optional-theme-fonts).

## Customizing

Reassign tokens at `:root` for theme-wide changes. For a scoped change, where
you reassign depends on the token:

```css
/* Brand-wide: rounder medium buttons */
:root {
  --ki-button-md-radius: 999px;
}

/* Scoped component token: a denser sidebar. Components read their own
   tokens where they are used, so any element works. */
.sidebar {
  --ki-list-item-padding-block: 0.25rem;
}

/* Scoped semantic or palette token: name the region's theme and reassign
   there. Only the root and theme roots recompute the tokens that alias it. */
[data-ki-theme='sidebar'] {
  --ki-surface-s1: var(--ki-surface-s2);
}
```

A semantic or palette token reassigned on a plain element changes only that
custom property: every token that aliases it keeps the value computed on the
root. The [theming guide](/docs/guides/theming/#theming-a-region) explains
regions in full.

Three rules keep customization safe:

1. **Prefer semantic over component tokens** — one semantic reassignment
   restyles consistently; fifty component overrides drift. Leave the palette
   to themes: an application that changes a ramp step changes every semantic
   token built on it, with no contrast check behind it.
2. **Re-check contrast when you re-theme.** Kimen's own token pairs hold
   4.5:1 for text and 3:1 for non-text UI in both schemes, verified by a
   blocking CI gate over the built stylesheets. Your overrides inherit the
   obligation, not the proof.
3. **If you would need `!important`, stop** — that is an API bug in Kimen;
   [report it](https://github.com/kimen-dev/kimen/issues).

## Machine-readable

The tokens ship as plain CSS custom properties in the built stylesheets
(`@kimen/tokens/css/core`, one `css/ki-<tag>` sheet per component, the
full `@kimen/tokens/css`, `css/material3`, `css/base`) — no runtime, no
preprocessor coupling. Per-component consumption is declared in the
[Custom Elements Manifest](/docs/resources/working-with-ai/), so
agents and tooling can read the styling contract the same way you do.
