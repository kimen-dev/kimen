---
title: Emitting specs with any LLM
description: Configure any model — any provider, any mode — to emit valid Kimen UI specs with @kimen/emitter, and close the reliability loop fail-closed.
---

`@kimen/emitter` derives everything an LLM integration needs from the same
catalog value your runtime validates and renders against — the built-in
catalog or one extended with
[your own registered components](/docs/guides/ui-spec/#registering-your-own-components).
One catalog in; a system prompt, a catalog-specialized JSON Schema and a
provider-neutral tool definition out, plus the two helpers that close the
reliability loop.

Install it next to the catalog it reads:

```sh
npm install @kimen/emitter @kimen/catalog
```

**Security model, up front**: everything the emitter produces is ADVISORY.
A derived schema or prompt improves a model's first-try validity; it
authorizes nothing. Budgets, the URL scheme allowlist, the purity wall and
catalog membership are enforced only by `validateUiSpec` and the guarded
renderer — always run emissions through them, whatever your provider's
"guaranteed" mode promises.

## Pick your integration mode

| Your provider supports | Use | Notes |
| --- | --- | --- |
| Nothing special (any chat model) | `catalogPrompt(catalog)` as a system-prompt block | The universal fallback; guidance verbatim + a validated example |
| Structured outputs / response schemas | `uiSpecJsonSchema(catalog, { target })` | `openai-strict` for all-required closed-object modes; `draft-2020-12` elsewhere |
| Tool / function calling | `uiSpecTool(catalog, { target })` | `{ name, description, inputSchema }`, provider-neutral |
| A strict mode without recursive schemas (Anthropic strict tools) | `draft-2020-12` on a regular, non-strict tool | No strict target exists: that subset cannot hold a catalog-specialized schema |

```ts
import { catalogData, createCatalog } from '@kimen/catalog';
import { catalogPrompt, uiSpecJsonSchema, uiSpecTool } from '@kimen/emitter';

const registered = createCatalog(myDefinition, { extend: catalogData });
if (!registered.ok) throw new Error(registered.issues[0].message);
const catalog = registered.catalog;

catalogPrompt(catalog);                                  // → { ok, artifact: string }
uiSpecJsonSchema(catalog, { target: 'openai-strict' });  // → { ok, artifact: JSON Schema }
uiSpecTool(catalog, { target: 'openai-strict' });        // → { ok, artifact: { name, description, inputSchema } }
```

Combine prompt + schema for best results: the schema constrains **shape**,
the prompt carries **judgment** (when to use which component). Both derive
from the same entries, so they cannot drift.

Every derivation accepts `{ components: [...] }` to subset large catalogs
and returns `{ ok: false, issues }` — never a throw — on version skew,
unknown subset members, malformed catalog values or exceeded provider
limits, always naming the offender. Identical inputs yield byte-identical,
version-stamped artifacts.

## Configure the cart surface

Use the same glyph list in the renderer realm and in every emitter artifact.
Pass a component subset and `verbosity: 'compact'` to shorten the system
prompt. Omit `verbosity` for the standard guidance.

```ts
import { catalogData, selectSpecIcons } from '@kimen/catalog';
import { catalogPrompt, uiSpecTool } from '@kimen/emitter';
import '@kimen/elements/icons/shopping-bag';
import '@kimen/elements/icons/tag';
import '@kimen/elements/icons/search';

const icons = ['shopping-bag', 'tag', 'search'] as const;
selectSpecIcons(icons);

const components = [
  'ki-card', 'ki-icon', 'ki-button', 'ki-input',
  'ki-select', 'ki-option', 'ki-textarea', 'ki-table',
];
const prompt = catalogPrompt(catalogData, { components, icons, verbosity: 'compact' });
const tool = uiSpecTool(catalogData, {
  components,
  icons,
  target: 'openai-strict',
  collect: { save: ['customerName', 'region', 'notes'], preview: ['region'] },
});
if (!prompt.ok || !tool.ok) throw new Error(JSON.stringify([...prompt.issues, ...tool.issues]));
```

If the model binds a `ki-button` to `save`, its `collect` is either `null` or
`{ "customerName": "f-name", "region": "f-region", "notes": "f-notes" }`.
Give the fields those node IDs and include `save` in the spec's top-level
`actions`. After normalization and validation, activating the button reports
the current field values to the host. The host chooses how to authorize
and handle that report.

The icon list can include custom registered names. An empty list, a blank
name or a vocabulary incompatible with a catalog prop returns
`invalid-option`. For a surface with no glyphs, leave `ki-icon` out of
`components` and omit `icons`. For a custom MCP Apps document, derive
artifacts from `surface.catalog` with `icons: surface.icons`.

## Always validate — the loop

```ts
import { renderUiSpec, validateUiSpec } from '@kimen/catalog';
import { normalizeEmission, repairPrompt } from '@kimen/emitter';

let spec = normalizeEmission(JSON.parse(modelOutput));
let report = validateUiSpec(spec, { catalog });
if (!report.ok) {
  const repair = repairPrompt(report);                    // ONE corrective message…
  spec = normalizeEmission(JSON.parse(await askModel(repair)));
  report = validateUiSpec(spec, { catalog });
  if (!report.ok) throw new Error('emission rejected');   // …then fail closed
}
renderUiSpec(spec, { surface, catalog });                 // renders the ACCEPTED emission
```

`normalizeEmission` strips exactly the placeholders strict-mode
all-required schemas force a model to emit (null-valued props, actions,
node IDs and collection maps) and touches nothing else — a value the model got wrong stays
wrong so validation reports it. `repairPrompt` formats every issue (code,
path, named offender) into a single corrective message; the
one-round-then-fail-closed policy is deliberate and fixed.

Provider "guaranteed JSON" modes do not replace validation: cross-field
rules (declared actions), budgets, the URL scheme allowlist and the purity
wall are boundary-only, and constrained decoding degrades on hard schemas.
