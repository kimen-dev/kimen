Kimen treats agent legibility as a deliverable: an API a capable agent
cannot wire correctly from its description alone is treated as a defect.
Everything below is **generated from the component sources** and shipped
with the package, so it can never drift from the code.

## llms.txt

The library, summarized for language models: every component with its
description, when-to-use / when-not-to-use guidance, typed props, events,
slots, CSS parts and curated runnable examples.

- In the repository: [`llms.txt`](https://github.com/kimen-dev/kimen/blob/main/llms.txt)
  at the repository root.
- In the npm package: `@kimen/elements/llms.txt` ships in the package files.

Point your tool at it — `@docs` in Cursor or Windsurf, or paste the URL into
a ChatGPT/Claude conversation — and the agent gets the whole component
contract in one document.

## custom-elements.json

The [Custom Elements Manifest](https://custom-elements-manifest.open-wc.org/)
is the interchange format the ecosystem reads: Storybook, IDE completions
(VS Code custom data, JetBrains web-types) and this site's own API tables
all consume it.

- In the npm package: the `customElements` field of `@kimen/elements` points
  to `generated/custom-elements.json`.
- On this site: served at
  [`/assets/elements/custom-elements.json`](/assets/elements/custom-elements.json)
  for tools that want to fetch it.

Kimen extends the standard schema with `whenToUse` / `whenNotToUse` fields
per component — the same guidance rendered on each component page.

## The catalog: from description to guardrail

Reading about components is half the story; **emitting UI safely** is the
other half. `@kimen/catalog` gives agents a validated output format — the
[UI spec](/docs/guides/ui-spec/) — and gives hosts a renderer that
enforces it fail-closed. For protocol-level integration, Kimen ships
adapters for [A2UI](/docs/guides/a2ui/) and
[MCP Apps](/docs/guides/mcp-apps/), where a Kimen surface reaches an
MCP host as a self-contained `ui://` resource.

To configure the model itself, `@kimen/emitter` derives the guidance
artifacts from the catalog in use: a system prompt carrying each
component's usage guidance verbatim, a catalog-specialized JSON Schema
with provider-strict lowerings, and a provider-neutral tool definition —
plus the normalize-and-repair helpers that close the reliability loop. See
[Emitting specs with any LLM](/docs/guides/emitting-specs/).

llms.txt tells a model what exists; the catalog constrains what it may
build; the emitter teaches any model to build it. Shipping all three is
the point.
